# US-015: Editar entrada del historial

**Status**: Sprint actual
**Sprint**: S12
**Epic**: [EPIC-03: Historial académico](../epics/EPIC-03.md)
**Priority**: Medium
**Effort**: S
**UC**: [UC-015](../use-cases/UC-015.md)
**ADR refs**: ADR-0032

## Como alumno, quiero modificar una entrada de mi historial para corregir datos o actualizar status

Como alumno, quiero un endpoint PATCH que modifique una EnrollmentRecord propia (corregir datos, actualizar status de "cursando" a "aprobada" al terminar el cuatrimestre), re-validando invariantes y, si la edición invalida una Review existente, emitir un evento que la mande a `under_review` (ADR-0032).

## Acceptance Criteria

### Backend

- [x] `PATCH /api/me/enrollment-records/{id}` con cambios parciales sobre `status`, `grade`, `approval_method`, `commission_id`, `term_id`.
- [x] Valida ownership: el `EnrollmentRecord.student_id` coincide con el `StudentProfile` del user.
- [x] Re-valida todas las invariantes del data-model (mismas que US-013).
- [x] Si la edición es destructive (cambio a `status = 'cursando'` cuando había una Review publicada anclada al enrollment): emite integration event `EnrollmentRecordEdited` vía Wolverine outbox (ADR-0030).
- [x] Reviews consume el event y pone la Review afectada en `status = 'under_review'` (ADR-0032).
- [x] Frontend pide confirmación explícita en destructive edits con copy claro: "Esto va a poner tu reseña en revisión".
- [x] Retorna 200 con el record actualizado.
- [x] Idempotencia del PATCH: si el client manda el mismo payload dos veces seguidas, segundo request es no-op (no emite evento, no actualiza updated_at). Implementado con check de equivalencia antes del save.
- [x] Existe un barrido de reconciliación gateado a staff que encuentra las reseñas publicadas cuya cursada volvió a estar en curso y les aplica la cuarentena. Es la red de contención de cuando el consumer agota los reintentos y el mensaje va al dead-letter.

### Frontend

- [x] Form de edit con confirmación condicional para destructive edits.

## Sub-tasks

- [x] Comando `UpdateEnrollmentCommand` + handler
- [x] Endpoint Carter PATCH
- [x] Detección de "destructive edit": comparar status anterior con nuevo. `aprobada` → `cursando` o `regular` → `cursando` con Review existente es destructive.
- [x] Integration event `EnrollmentRecordEdited` con outbox durable (Wolverine)
- [x] Handler en módulo Reviews que invalide (mueve a `under_review`) la review afectada
- [x] Integration tests: edit no-destructive, edit destructive con review (verificar que la review pasó a under_review post-event)

## Notas de implementación

- **Cross-BC via Wolverine outbox**: ADR-0030. El evento `EnrollmentRecordEdited` no se procesa síncrono; se persiste en el outbox y Wolverine lo entrega a Reviews after commit. Garantiza atomicidad con el update del enrollment, sin acoplar transaccionalmente los dos módulos.
- **Por qué `under_review` y no `removed`**: ADR-0032. La edición destructive no implica que la reseña sea inválida (el alumno puede haberla escrito antes y la cursada cambió por error administrativo). Mover a `under_review` da espacio a moderar caso por caso.
- **Ownership como primer check**: si el `student_id` del enrollment no es el del user, retornar 404 (no 403) para evitar enumerar IDs ajenos.
- **La recuperación se deriva del dato, no de un flag.** El AC original marcaba la reseña con
  `needs_revalidation` cuando el evento fallara, y eso es circular: si el evento no llega, Reviews
  no se entera, y Reviews es quien tendría que poner la marca. Una reseña publicada cuya cursada
  está en curso ya es contradictoria por sí sola, así que el barrido la encuentra sin depender de
  que alguien la haya marcado. Un flag puede quedar sin escribir; el dato no puede mentir sobre sí
  mismo.
- **El outbox no es el agujero.** `PersistMessagesWithPostgresql` + `AutoApplyTransactions` +
  `UseDurableLocalQueues` garantizan que el evento se persista en la misma transacción que el cambio
  de la cursada y sobreviva a un restart. Lo que queda descubierto es el consumer: si agota los
  reintentos, el mensaje va al dead-letter y nadie se entera. Eso es lo que cubre el barrido.
- **El historial tuvo que abrir el id de la cursada.** `TranscriptEntry` mostraba código, nombre,
  estado y nota, y nada con qué direccionar el PATCH: la pantalla mostraba el dato equivocado y no
  había forma de arreglarlo. El read ahora lleva `id`, `subjectId`, `commissionId` y `termId`, que
  es también lo que precarga el formulario.
- **Las invariantes cross-field del front viven compartidas** (`lib/enrollment-invariants.ts`).
  Llegó el segundo consumidor real (alta y edición), y es el mismo movimiento que ya había hecho
  el aggregate cuando `Create` y `Update` pasaron a compartir un único `ValidateInvariants`: una
  regla que valga distinto en el alta que en la edición sería un bug, no una diferencia.
- **La confirmación solo aparece cuando hay algo que confirmar.** La page resuelve contra
  `GET /api/reviews/me` si esa cursada tiene una reseña **publicada**; sin ella el consumer no hace
  nada, así que advertir sería inventar una consecuencia. Es la misma condición que usa el backend
  para publicar el evento, así que el aviso no se puede desincronizar de lo que pasa.
- **Sin mockup propio: la pantalla es el form del alta menos la materia.** El canvas no tiene una
  vista de edición de cursada, y el AC pide un form, no una vista nueva. Copiar la forma del alta
  (mismos campos condicionales, mismo layout) es lo que hace que corregir se parezca a lo que el
  alumno ya hizo una vez; inventarle una pantalla distinta sería improvisar visuales.
- **No hay endpoint de DELETE de enrollment todavía**: por simplicidad. Si un alumno quiere "borrar" una cursada, edita a `abandonada`. Si en el futuro hay un caso real para hard-delete, se separa en US.
